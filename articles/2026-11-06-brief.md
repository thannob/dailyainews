## ข่าวเด่น 24 ชั่วโมงที่ผ่านมา

### 1. Microsoft Research ปล่อย PDD Kit — พิสูจน์ความถูกต้องของโค้ดที่เอเจนต์เขียนด้วย Verus — [Microsoft Research](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)

Alex Lavaee และ Matthai Philipose จาก Microsoft Research เผยแพร่ research preview ชื่อ PDD Kit (Proof-Driven Development Kit) วันที่ 5 พฤศจิกายน 2026 โดยเสนอ workflow ที่แปลง "intent" ของนักพัฒนาเป็น formal specification บน Verus, ให้ coding agent เขียน Rust ควบคู่กับ proof annotations แล้วรันพิสูจน์ใน CI ขั้นตอนหลักแบ่งเป็น `pdd-plan` (ถามคำถามจนได้ intent artifact แล้วแปลงเป็น Verus spec หรือเป็น informal test spec เมื่อ Verus ยังเอื้อไม่ถึง), `pdd-prove` (สร้าง proof + test) และ `pdd-ship` (รัน proof ซ้ำทุกครั้งที่โค้ดเปลี่ยน) ผลลัพธ์แต่ละส่วนถูกแปะป้ายเป็น "formally verified" (มี Verus proof) หรือ "empirically verified" (ครอบคลุมด้วยเทสต์) โดยมี Trusted Computing Base ขีดเส้นระหว่างสองประเภท

Case study ของทีมคือร้านค้า Rust ชื่อ Pet Store ประมาณ 5,000 บรรทัด — backend เป็น Axum + SQLite, frontend เป็น Leptos + WebAssembly — ทีมเขียน `ensures` clause 8 ข้อบน `login_flow` และ PDD Kit สามารถพิสูจน์ได้สำเร็จพร้อมเผยบั๊กที่มีอยู่ ส่วนที่อยู่นอก proof มี 6 จุด ได้แก่ DB lookup, การเช็ค bcrypt password, การเซ็น token, และ clock — แต่ละจุดถูก model ด้วย contract และจะถูกตรวจด้วยเทสต์แทน ทีมย้ำว่า `check_password` กับ DB lookup คือจุดที่ "แบกงานไว้มากที่สุด" และเพิ่ม reviewer-agent สอง instance คอยตรวจ spec กับทำ mutation check (ตั้งใจปลูกบั๊กหนึ่งต่อหนึ่ง clause) เพื่อยืนยันว่าแต่ละ clause กินงานจริง

สำหรับอาจารย์และนักศึกษา งานนี้เป็นกรณีศึกษาที่ดีในการสอนความต่างระหว่าง review (ดูว่าโค้ด "ดูถูก") กับ proof (พิสูจน์ว่าโค้ดถูกตาม specification สำหรับทุก input) รวมถึงแนวคิด TCB ที่ชี้ว่าการพิสูจน์มีขอบเขตเสมอ — ส่วนที่อยู่นอกขอบเขตก็ยังอาศัย assumption ที่ต้องเชื่อ ฝั่งผู้เชี่ยวชาญ AI มองว่าเวิร์กโฟลว์ plan → prove → ship ตอบโจทย์ที่เอเจนต์ผลิตโค้ดเร็วเกิน review รายบรรทัด และเทสต์ที่เอเจนต์เขียนเองก็เสี่ยงต่อ "ความครอบคลุมปลอม" แต่ข้อจำกัดใหญ่ยังคือ Verus รองรับเฉพาะ Rust และ proof ยังกินแรงคนเยอะ ส่วนโปรแกรมเมอร์ที่ดูแลระบบ auth, payments, หรือ token signing ควรจับตา — การย้ายภาระจาก "เทสต์ที่เขียนเองโดยเอเจนต์" ไปที่ "proof ที่ตรวจต่อกับ spec" คือทิศทางที่น่าทดลอง แต่ยังเหมาะกับส่วนเล็ก ๆ ที่มูลค่าสูงก่อน ไม่ใช่ทั้ง codebase
